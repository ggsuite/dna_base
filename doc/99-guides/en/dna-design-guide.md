# DNA Design Guide

How the DNA system works and how DNA packages are designed. The DNA
keeps a family of repositories consistent: shared guides, Claude
skills, scripts and configuration are written **once** in DNA packages
and **instantiated** into every consuming project.

Two things are easy to confuse:

- **Helix is the engine** (formerly `gg_dna`) — it resolves, merges
  and instantiates DNA. It ships no `dna/` folder and therefore no
  content of its own.
- **The DNA is the content** — it lives in DNA packages (`dna_base`,
  `dna_dart`, `dna-ts`, `ds-dna`, …). That is where you edit anything
  projects should inherit.

## The replica layout

A DNA package is a normal pub/npm package that ships a `dna/` folder.
That folder is a **replica of a project root** — Helix copies its
content to the real locations, the copies are called **instances**:

| Path in the DNA                        | Instantiated to                |
| -------------------------------------- | ------------------------------ |
| `dna/dot-vscode/settings.json`         | `.vscode/settings.json`        |
| `dna/LICENSE`                          | `LICENSE`                      |
| `dna/doc/99-guides/en/test-guide.md`   | `doc/99-guides/en/test-guide.md` |
| `dna/dot-claude/skills/init/SKILL.md`  | `.claude/skills/init/SKILL.md` |
| `dna/_vars.json`                       | — (private)                    |

- **Dotfiles are escaped** with a `dot-` prefix, because
  `dart pub publish` silently drops every path with a leading dot — an
  unescaped `dna/.vscode/` never reaches a pub-installed consumer.
  `dot-` is the only accepted escape; a `dot_`-escaped path fails the
  placed test with the rename it expects.
- **Private:** path segments starting with `_` (`_vars.json`,
  `_drafts/…`) stay inside `dna/` and are never instantiated.
- **Consumed by Helix itself:** `*.overrides.md`, `*.overrides.json`
  sidecars, `global.overrides.md`, and the two manifests
  `_dna.json` / `_generated.json`.
- **Forbidden instance targets:** `.git/**` and `CLAUDE.md` — a
  `dna/CLAUDE.md` is skipped with a warning. `CLAUDE.md` is filled via
  the managed block instead (see below).
- **File names instantiate exactly as written** — no case conversion.
  Our naming rule: hyphens for all DNA folders and files
  (`test-guide.md`, `dot-claude/`); only Dart folders (`lib/`,
  `test/`) use snake_case, because Dart requires it.

## Distribution: dependencies + inheritance

DNA packages are distributed through the normal package managers —
no cloning, no custom fetching:

- A **project** declares its DNA(s) as dev-dependencies
  (`pubspec.yaml` / `package.json`).
- A **DNA** declares its parent DNAs as regular dependencies — pub and
  pnpm install the whole inheritance tree transitively.
- **Layers are named by package name**, never by a path. Lock files
  pin identity (ecosystem, version); `node_modules/` and
  `.dart_tool/package_config.json` supply the location.
- A DNA published to both registries is **one** layer: the npm scope
  is dropped when folding names, so `@tssuite/dna-base`, `dna_base`
  and `dna-base` are the same identity (node wins when both are
  installed).
- For local development, `gg_localize_refs` points
  `pubspec_overrides.yaml` / `pnpm-workspace.yaml` at sibling
  checkouts — Helix follows whatever the package manager resolved.

**Merge order:** the `layers` list is the single source of truth —
parents before children, diamonds deduplicated (first topological
position wins), cycles are errors. **The last layer wins** on path
collisions.

## Roles: `dna/_dna.json`

`dna/_dna.json` is the only place DNA configuration lives (inside
`dna/` because that is the one folder both ecosystems publish). A
`dna/` folder **without** `_dna.json` is a hard error.

```jsonc
{
  "version": 1,                    // required
  "role": "project",               // "dna" for DNA packages
  "layers": ["dna_base"],          // package names, application order
  "vars": { "<your-project>": "my_project" },
  "claude": { "claudeMdInclude": ["doc/99-guides/en"] }
}
```

- **`role: "project"`** (default) — a consumer: `dna/` is fully
  generated by Helix. Never edit it — except `_dna.json`, which is
  yours.
- **`role: "dna"`** — a DNA repository: `dna/` is authored by hand,
  never overwritten, and applied to the repo itself as the last
  (winning) layer — a DNA repo eats its own dog food. This declaration
  is what makes a package usable as a layer at all.

Helix only ever *reads* `_dna.json`. Its bookkeeping — resolved
layers, versions, hashes, and the list of instances it owns — goes to
`dna/_generated.json`, which is machine-owned: never edit it.

## The placed test: instantiate + verify on every test run

`helix init` is the only CLI command (`helix sync` was removed). It
places a wrapper test (`test/dna/dna_test.dart` and/or
`test/dna/dna.spec.ts`) and the `_dna.json` skeleton. From then on
**every test run instantiates the DNA**: resolve layers → merge →
apply overrides → substitute variables → reconcile with the project.

| Situation                                   | Result |
| ------------------------------------------- | ------ |
| Everything up to date                       | Green, no writes |
| The DNA produced updates                    | Files written and committed as `#gg: generated DNA` |
| An instance was edited locally              | DNA content wins; the local edit is backed up to a system-temp folder and the path is printed |
| A non-instance file would be overwritten while carrying uncommitted work | Test fails without writing, names each file |
| `LICENSE` missing                           | Test fails |

Rules that follow:

- **Instances belong to the DNA.** To change one, edit the DNA layer
  that owns it (or `dna/` in a `role: dna` repo) — the next test run
  propagates the change. Hand-edits to instances are overwritten (the
  backup path is printed).
- **Per-file guard:** every other file a run would overwrite must be
  committed first — DNA changes always appear as a reviewable diff on
  top of a commit. Unrelated dirty files never block a run.
- Existing project files that a DNA also ships are **adopted**
  (overwritten — git history is the backup). Instances no longer
  produced by any layer are removed, along with folders they leave
  empty.

Getting started in a consumer:

```bash
dart pub add --dev dna_dart helix   # declare DNA(s) + engine
dart run helix init                 # place test + config skeleton
git add -A && git commit -m 'Add DNA'
dart test                           # first run instantiates + commits
```

## Overrides: higher layers patch lower layers

### Markdown (`X.overrides.md`)

The target file offers two kinds of anchors:

- `## [@tag] Heading` marks the whole section as replaceable.
- `{{@tag:default}}` marks an inline string with a default.

A higher layer ships `X.overrides.md` next to the same path,
containing heading-form blocks (replace the section) or
`<!-- @tag --> … <!-- @tag -->` blocks (rewrite the string). A
`global.overrides.md` in the layer's `dna/` root rewrites string tags
across **all** files of lower layers. Markers survive layer
application — even higher layers can override again — and are stripped
from the final instances. Fenced and inline code are never touched.

### JSON (`X.overrides.json`)

A same-path `X.json` in a later layer replaces the file. A sidecar
`X.overrides.json` merges field-wise:

- objects deep-merge, scalars replace,
- `"key": null` deletes the key,
- `"key!"` replaces the value outright (no merge),
- `"key+"` appends to an array (deduplicated).

JSONC (comments, trailing commas) is tolerated; structurally patched
files are re-emitted comment-free, untouched files are copied
byte-identical. YAML supports whole-file replacement only.

## Variables

Layers define variables in `dna/_vars.json` — camelCase keys that
**must** start with `dna` (a key without the prefix fails the placed
test). Variable files deep-merge across layers (`null` deletes); the
target's `_dna.json` `vars` override last. References are replaced
case-adaptively in every text file:

| Reference          | Renders as (value `my-project`) |
| ------------------ | ------------------------------- |
| `<your-project>`   | `myProject`                     |
| `<your-project>`   | `MyProject`                     |
| `<your-project>` | `my_project`                    |
| `<your-project>` | `MY_PROJECT`                    |
| `<your-project>` | `my-project`                    |

Non-identifier values (sentences, spaces) are inserted verbatim in all
forms; unknown references stay literal. Values may reference other
variables (expanded until stable, at most 10 passes; cycles are
detected and reported with the path that closes them).

## CLAUDE.md: the managed block

`CLAUDE.md` is never a DNA instance. Instead, `claude.claudeMdInclude`
in the target's `_dna.json` lists files/folders that get one
`@`-import line each between `<!-- helix:claude_md:start -->` and
`<!-- helix:claude_md:end -->` — folders expand to their `.md` files,
missing entries fail the run. Claude Code expands the imports at every
session start, so listing `doc/99-guides/en` makes **all guides
mandatory reading on every start**. Content outside the block belongs
to the project and is never touched.

## Design rules for DNA content

- **Edit the DNA, never the instance, never Helix.** A change lands in
  the owning layer; the placed test propagates it everywhere.
- **One concern per DNA package.** `dna_base` carries what every repo
  shares; language DNAs (`dna_dart`, `dna-ts`) and organization DNAs
  layer their specifics on top via overrides — they do not fork files.
- **Design for overriding:** tag sections (`## [@tag]`) and values
  (`{{@tag:default}}`) that higher layers will plausibly replace,
  instead of forcing them to duplicate whole files.
- **Use variables** (`ggsuite`, `https://github.com/ggsuite`, …) instead of
  hardcoding names — consumers override them in `_dna.json`.
- **Everything in `dna/` is published** — no secrets, no drafts
  outside `_`-prefixed folders.
- Documentation is written for humans; the AI consumes the same files
  via the managed CLAUDE.md block — see the
  [Multi-Language Guide](./multi-language-guide.md) for the en/de
  mirror rule.
